Phase 1 Data Foundation Weeks 1 to 3 · nearly done
1.1
Audit OSM coverage and lock the source stack
DoneData

OSM is the right primary source, open, structured, and editable by anyone including you, but its coverage of Canadian indie bookstores is uneven. Toronto, Montreal, and Vancouver are reasonably mapped. Smaller cities and rural areas are thin. The audit confirmed a multi source strategy from day one.

Source stack, in priority order: OSM (primary, free, community maintained), Google Places API (gap filling, best phone and hours data), Wikidata (structured secondary for established stores), the CIBA member directory (manually curated, high trust), ALQ for Quebec francophone stores, and BookNet Canada data where available. Community submissions handle the long tail.
  • Overpass query for shop=books across all provinces, exported, with the thin regions flagged (Atlantic Canada, the Prairies, the territories).
  • Cross referenced against the CIBA directory at ciba.ca. Any CIBA store missing from OSM is both an addition candidate and a warm launch contact.
  • Google Places budget set with billing alerts. The free tier covers an initial province by province seed comfortably.
  • Wikidata checked for instance of: bookshop with a Canadian location, which catches long established community anchors.
  • No Yellow Pages, Yelp, or similar aggregators. Stale data and hostile licensing.
1.2
Design the schema and provision Supabase with PostGIS
DoneTechnicalData

The schema is the contract everything else builds against. It is written and provisioned. It accommodates multiple sources, tracks provenance, supports filtering, and leaves room for community enrichment.

Tables in place: stores (canonical record), store_sources (one row per source per store), events, submissions (community queue), change_log (audit trail and diff feed), spotlights, and specialty_tags. Enums, indexes, RLS policies, and two PostGIS functions, stores_near and stores_geojson, are live.
  • Opening hours stored twice: the raw OSM string as source of truth, plus a parsed JSONB column for the open now filter and display. A parser bug never loses data.
  • Soft deletes on stores only (is_deleted plus deleted_at). Hard deletes elsewhere, with change_log as the safety net.
  • specialty_tags is a controlled vocabulary with French labels: used books, rare and antiquarian, children's, francophone, Indigenous, LGBTQ+, genre fiction, academic, art and design, multilingual. Resist free text.
  • data_quality_score (0 to 100) computed from completeness: has phone, website, hours, human verification, photo. Use it to surface records that need attention.
  • PostGIS geography types for coordinates. stores_near powers radius search, stores_geojson powers the map source.
1.3
Scaffold the pipeline repo
DoneTechnical

The pipeline is a standalone Python repository, separate from the Next.js app. The scaffold is built: folder structure, dependencies, and an AGENT.md that carries full project context into Claude Code sessions so generated code stays consistent across sittings.

Three jobs by design. Seed runs once and fills the database. Sync OSM runs weekly and diffs against OpenStreetMap for new stores, changes, and possible closures. Enrich Google runs monthly and refreshes hours and phone for stores with a google_place_id.
  • Layered layout: sources/ (fetch and lightly parse), transforms/ (shape into the stores schema), db/ (all database calls, nothing raw in job files), jobs/ (seed, sync, enrich), scripts/ (click CLI entry points).
  • pyproject.toml with Hatchling. Core deps: supabase-py, httpx, pydantic and pydantic-settings, structlog, click, tenacity, osm-opening-hours, phonenumbers, python-slugify. Dev group: pytest, ruff, mypy.
  • AGENT.md records the architecture rules, schema decisions, source priority, the hours JSONB shape, the sync diff logic, env vars, and testing conventions. Keep it current as the contract for AI assisted sessions.
1.4
Write the seed, sync, and enrich jobs
NextTechnicalData

This is the live next step. The scaffold is ready and the schema is waiting. Write the three jobs against the db/ layer and get real data flowing.

  • Seed: normalize each OSM feature into the stores schema, store osm_id, set data_source = 'osm'. Map name, addr:* tags, phone, website, opening_hours. Overpass query: area ISO3166-1 = CA, node and way shop=books, out body center (center gives a lat/lng for ways).
  • Sync OSM: fetch the current Overpass result, compare osm_id against the database, and categorize into new (insert), modified (update with a change_log entry), and missing (flag for human review). Never auto close, never auto delete.
  • Enrich Google: for any store with a google_place_id, fetch current hours and phone and update. Run monthly, it burns quota.
  • Schedule sync and enrich with GitHub Actions cron jobs. Keep run logs, Overpass times out occasionally and you want a record of missed runs.
  • Wrap every external call in tenacity retry. Log through structlog so the Actions output stays readable.
1.5
Run the seed and QA the dataset
Data

The pipeline gives you a foundation. Manual QA makes it trustworthy. Do not launch on unreviewed automated data. A map full of closed stores or wrong addresses poisons early word of mouth before the site has credibility to spend.

  • After the seed, sort by data_quality_score ascending. The lowest scores are the likeliest errors. Start there.
  • Cross reference the CIBA directory. Add any missing members directly, mark is_verified = true and data_source = 'ciba'.
  • Spot check at least 20 stores per major province (ON, QC, BC, AB) against Google Maps. Mark verified and date it.
  • Build a fast admin view (Supabase Studio or a quick Next.js admin page) for manual edits. You will do a lot of these early.
  • A needs review flag lets you triage. Stores needing research go to a queue rather than blocking the rest.
Phase 2 MVP Build Weeks 3 to 7
2.1
Scaffold the Next.js app and wire Supabase
Technical

The app is its own repository. Build with the App Router. This is a content site with dynamic filtering, so server components fit the listing and detail pages, with client components only where interactivity demands it (map, filters, search).

  • Stack: Next.js (App Router), Supabase (data and auth), Mapbox GL JS, Tailwind, Resend (form email), Vercel (hosting). Confirm the current Next.js major before locking it, the plan was written against 15.
  • Routes, kept flat: / (map home), /stores/[slug] (store detail), /events (book fairs), /about, /submit (correction and feedback).
  • Environment variables for Supabase, Mapbox, and Resend from day one. .env.local locally, Vercel env vars in production. Never commit keys.
  • RLS is already configured at the database. Public read on verified stores, writes only through the authenticated service role used by the pipeline, submissions land in their own table.
  • Use @supabase/ssr, not the legacy auth-helpers.
2.2
Build the map with clustering and filters
Do firstTechnical

The map is the product. Everything else is supporting infrastructure. Build it first, build it well, and treat mobile as a first class concern. A lot of people will use this while standing near a store or hunting for one nearby.

Architecture: serve all coordinates from the existing stores_geojson PostGIS function through a Next.js API route or a Supabase Edge Function. The client loads it once on mount, renders it as a Mapbox source with clustering, and runs every filter client side on the loaded data. No round trips on filter changes. For a dataset this size (roughly 400 to 700 stores) this is entirely viable.
  • Mapbox GL JS clustering with custom cluster sizes. Clusters show a count when zoomed out and dissolve into markers past about zoom 10.
  • Custom marker: a small open book or bookmark glyph in a distinctive colour, crisp at 16 to 24px. This is where the map stops looking generic.
  • Filter panel: specialty checkboxes, a province dropdown, an open now toggle (uses the parsed hours JSONB), and a text search across name and city. Collapsible on mobile.
  • Marker click opens a slide up panel (mobile) or sidebar (desktop) with the store detail and a suggest a correction link, without navigating away from the map.
  • A near me button centers on browser geolocation. Do not prompt for location on load, wait for the user to ask.
2.3
Build store detail pages with SEO
TechnicalSEO

Pages at /stores/[slug] do two jobs: a shareable, linkable URL per store, and enormous long tail SEO value. "Indie bookstores in Sudbury" is winnable for a site like this, and a dedicated page per store is how you win it.

  • Slugs from name plus city (the-bookshelf-guelph), numeric suffix on duplicates. Store the slug, do not compute it on the fly.
  • generateStaticParams with ISR on store pages, revalidate on a 24 hour cycle. Stores do not change daily and you do not want to rebuild on every pipeline run.
  • Page content: name, full address with a get directions link, phone, website, hours formatted nicely (not the raw OSM string), specialties as readable tags, a small single store map, and an OpenStreetMap attribution with a contribute link.
  • JSON-LD LocalBusiness structured data on every store page: name, address, geo, telephone, url, openingHours. This is how Google builds rich local results.
  • The suggest a correction link pre fills the form with the store name and id so submissions arrive with context.
2.4
Build the events calendar
TechnicalData

The events calendar is manually curated, there is no reliable automated source for Canadian book fairs. That is a strength. A human reviewed calendar is a reason to return and it positions you as an active steward rather than a passive data mirror. Book fairs ship first, in store events stay a schema placeholder.

Seed events: Word on the Street (Toronto, Halifax), Expozine (Montreal), Ottawa Small Press Book Fair, Victoria Book Fest, Vancouver Writers Fest, Winnipeg International Writers Festival, Eden Mills Writers Festival, and the provincial library association fairs. Independent Bookstore Day (last Saturday in April) is the recurring annual anchor.
  • Events schema is in place: name, description, event_type, start and end date, location, city, province, lat, lng, website, is_recurring, linked_store_id (nullable).
  • Calendar UI: a list or month toggle, default to list. Most visitors want what is coming up near me in the next 60 days.
  • Filter by province and event type. An add an event link routes to the submission form, community events go to the review queue first.
  • Plan for an events map layer (a toggle adding event pins over the store map) as a later enhancement, the data model already supports it.
  • Eventbrite and Meetup APIs are optional supplementary sources for author readings, useful for the larger stores that use them.
2.5
Build the About page and submission form
ContentTechnical

The About page does more work than it looks. For a community data resource, transparency about method builds trust. People need to know why a store is or is not listed, how the data stays current, and how to help.

  • Sections: what the site is and why it exists, how stores are found (OSM plus CIBA plus ALQ plus community), what verified means and how often data is checked, how to suggest a correction or add a store, and who built it. Keep it warm and personal, a labour of love, not a corporate directory.
  • Explain the OSM connection plainly and link to how people contribute to OSM directly. That creates the flywheel: people improve OSM, your pipeline picks it up automatically.
  • The submission form has two paths: report a problem with an existing store (needs a store name or link) and add a missing store (free form). Both write to submissions and fire a Resend notification to you.
  • A data freshness line somewhere visible (Store data last synced: date) signals active maintenance. It matters more than it sounds.
Phase 3 Launch Weeks 7 to 9
3.1
Deploy to Vercel and lock the production stack
Do firstTechnical

Get something live at indiebooksatlas.ca early, even imperfect. An MVP in the wild collects real feedback. A perfect build that ships three months late collects nothing.

  • Register indiebooksatlas.ca. If .ca is gone, .com works, but .ca signals belonging for a site about Canadian stores.
  • Deploy to Vercel, connect the repo for preview deployments on every PR. Production branch main, manual promotion from staging.
  • Analytics: Vercel Analytics or Plausible. Plausible is privacy respecting with a Canadian data option and will not make you feel like you are surveilling your readers. Avoid Google Analytics.
  • Sitemap at /sitemap.xml covering all store pages, events, and about. Submit to Google Search Console on launch day.
  • Uptime monitoring (UptimeRobot free tier). Know before your users do.
3.2
Reach out to CIBA, ALQ, and the bookstore community
Do firstGrowth

The single highest leverage launch action is getting the bookstore community itself to know the site exists. One story share from a beloved local store reaches exactly the audience you want. Cold outreach here is not spam, you have literally built them a free listing.

  • Email CIBA. Explain the site, note that their members are already listed, ask about a mention in the member newsletter. Warm ask, enormous upside.
  • Email ALQ the same way for the Quebec francophone community. It is distinct and very well organized, the right partner for that audience.
  • Email or DM 10 to 15 well known indie stores individually, at least one per province. McNally Robinson, Type Books, Librairie Drawn and Quarterly, Shelf Life Books, Bolen Books, Bookmark in Halifax. Personalize each, link straight to their live store page.
  • Post in the Canadian book community on Bluesky (genuinely active there) with a map screenshot and a short "I built this, here is why."
  • Relevant subreddits with honest framing: r/CanadianBookClub, r/books with a Canadian angle, and city subreddits for your strongest regions. Do not astroturf.
  • Pitch CBC Books, 49th Shelf, and Open Book Ontario. Ten minute emails to editorial contacts, worth it.
3.3
Time the launch around Independent Bookstore Day
GrowthSocial

Independent Bookstore Day falls on the last Saturday of April. It is the one day indie bookstore content trends organically, readers are primed to celebrate local stores, and the stores themselves are posting. A launch on or just before it gives you a wave to ride.

  • If the build is ready, soft launch the week before (site live, store outreach) and push publicly on IBD itself. If you miss it, the next natural window is fall festival season (September to October).
  • Prepare IBD content in advance: what IBD is, a map screenshot highlighting participating stores, and a find your nearest participating store call to action.
  • Reach out to stores about their IBD events two weeks ahead. Offer to list the event. You get content, they get a reason to share the site.
Phase 4 Community and Social Months 2 to 4
4.1
Establish the social presence and rhythm
SocialGrowth

The social presence is not about broadcasting the site. It is about being part of the community the site serves: amplifying individual stores, celebrating booksellers, and reliably boosting Canadian literary culture.

Platform priority: Instagram first (the indie bookstore world is heavily visual and lives there), Bluesky second (the Canadian literary community migrated there and engagement is real), Threads as a low effort Instagram mirror. Skip X and Facebook, the first is a diminishing return for this audience and the second is too complex for a solo operator.
  • Handle @indiebooksatlas everywhere. Secure it now even on platforms you are not posting to yet.
  • Rhythm: three posts a week is sustainable. One bookseller spotlight, one event highlight, one general Canadian books post.
  • A simple Canva or Figma template for spotlight and event cards. Consistent identity makes the account recognizable in a feed.
  • Always tag the featured store. That is how you earn reshares, and a reshare reaches their existing customers directly.
  • Engage with store and book community accounts consistently in the first months. Visibility is earned through engagement, not just posting.
4.2
Build the bookseller spotlight format
SocialContent

The spotlight is the heart of the content strategy. Indie stores are run by real people with deep knowledge, and surfacing that is what separates the atlas from a generic directory. This is community journalism, not marketing.

  • Social format: a store photo (from the store's own Instagram with credit, or Street View as fallback), three to five lines on the store's character and why it is worth a visit, the city, and a link to the listing. Human voice, no corporate tone.
  • Deeper site spotlights: a Q and A, low effort to produce. Email five short questions, publish the answers lightly edited. "What is the strangest book you have been asked for" beats "what are your hours."
  • Prioritize underrepresented regions early: the Maritimes, the Prairies, the North. These stores rarely get national coverage, they are appreciative, and it corrects the Toronto and Montreal gravity in Canadian media.
  • A featured field on the store record, wired to the detail page with a small indicator, gives a spotlight permanence beyond the 48 hour life of a post.
4.3
Add curated reading lists and staff picks
ContentGrowth

A store that specializes in Indigenous literature or Quebec fiction or kids' books is more useful to a visitor if the listing says what they will find. Staff picks and specialty notes are an invitation a bare address is not.

  • A staff_picks field on the store record, short free text with optional titles, populated entirely through community contribution, never automated.
  • In every Q and A, ask "what is a book you have hand sold a hundred times" and put the answer in the listing. Editorial texture and a genuinely useful signal.
  • Link to each store's Bookshop.org page where one exists. Bookshop.org has a Canadian affiliate program and stores earn a cut. It is a service to the store and a natural tie in to your own affiliate setup (see Phase 5).
Phase 5 Sustain and Expand Months 4+
5.1
Build a data health dashboard and triage workflow
TechnicalData

Long term credibility depends entirely on data quality. A closed store still on the map is worse than no store, it erodes trust in every other listing. Build the maintenance workflow before the first angry submission, not after.

  • An internal admin dashboard (a protected Next.js route with Supabase auth): total stores, stores flagged for review, pending submissions, last sync date, stores unverified in 90+ days, and stores with data_quality_score below 40.
  • A weekly email digest to yourself (Resend plus a cron): new submissions, OSM sync results (new, changed, flagged for closure), and stores whose Google Places fetch errored. Maintenance stays visible without logging in.
  • A quarterly data audit: one session every three months to work the review queue, re verify the lowest scores, and clear backlogged corrections. Block it in your calendar like any other commitment.
  • Push verified corrections back to OSM. When you fix hours or an address, make the same edit upstream. Good citizenship, and the fix propagates beyond your site.
5.2
Pursue non sleazy monetization
Revenue

Revenue should feel like a natural extension of the site's values, supporting independent bookselling rather than exploiting it. None of the options below need ads or compromise the directory's integrity, and each aligns your income with the site working as a genuine resource.

The Bookshop.org affiliate program is the cleanest fit. Bookshop.org exists to support independent stores, and a percentage of every sale through your links goes to indie booksellers. Linking a store's Bookshop page from their listing serves the reader and the store and earns a small commission. Set it up first.
  • Apply to Bookshop.org's affiliate program (Canadian storefront). Add your tag to Bookshop links. It earns on any purchase within 30 days of a click, not just the linked title.
  • Once traffic is meaningful, approach CIBA about sponsorship. A proud supporter badge and a mention in member communications for a modest annual fee is the kind of arrangement that feels right and keeps you independent.
  • An optional claim your listing flow: free to claim, a small annual fee (CAD 40 to 80) for staff picks, a longer description, event listings, and search priority. Not pay to list, unclaimed stores still appear in full. Pay to enrich.
  • A support this project page with Ko-fi or Open Collective. Frame it as keeping the lights on, one footer link, not prominent.
  • No AdSense, no display advertising. The aesthetic damage alone is not worth it and the community will notice.
5.3
Expand to used, antiquarian, and francophone stores
DataGrowth

The MVP treats all indie stores as one category. Over time, distinct subcommunities want a clearer signal the atlas speaks to them. Used book hunters, Quebec francophone readers, and antiquarian collectors are all underserved by generic directories.

  • Used and antiquarian stores are already covered by the OSM shop=books plus second_hand=yes convention. Make sure the Overpass query captures it and the filter UI surfaces it.
  • For Quebec, work with ALQ the way you do with CIBA. The francophone bookstore culture is distinct and very well organized.
  • Add a francophone specialty filter explicitly, separate from a language tag. A store can be bilingual and primarily francophone at once, the specialties array handles that better than one language field.
  • Consider a French version of the About page and submission form. Not the whole site, but the community facing pages in both official languages signals the atlas belongs to all of Canada.
5.4
Run it as proof on DaveBeach.me
GrowthProfessional

With the Haunted Atlas now leading the portfolio, the atlas's job here shifts. It is no longer the headline, it is finished, shippable proof: a live production system that demonstrates the exact stack you sell, OSM pipelines, PostGIS, Mapbox, Next.js, automated sync, and community scale data stewardship. Quiet credibility, not the marquee.

  • Write one case study for DaveBeach.me on the technical decisions: why OSM, how the sync diff works, the PostGIS queries behind the map, and the data quality challenges unique to community maintained data. The kind of writing that converts leads.
  • Keep it as a demonstration project for GIS clients who need similar data driven maps: heritage registries, community directories, environmental monitoring. The patterns transfer directly.
  • Open source the pipeline scripts. An OSM to Supabase sync for point of interest data is genuinely useful to other developers and positions you as a contributor to the GIS community, not just a consumer.
The bigger picture

Indie Books Atlas is community infrastructure disguised as a website. The stores need it, the readers need it, and the Canadian literary community needs a resource that does not depend on a US tech company's goodwill or a commercial directory's business model. It is also a genuine geospatial showcase, but with the Haunted Atlas leading the portfolio it earns its keep as finished proof rather than the headliner. Build it like it will last twenty years, because it might.
